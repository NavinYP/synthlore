1 · What the pilot proved

The pilot is a complete end-to-end run at reduced scale: a 34-entity world, 75 documents (~34,300 words), 25 AI-generated images, 6 programmatic fact plates, and a generated + verified Q&A benchmark. Every mechanism the full corpus depends on ran for real — same code paths, same models, same packaging.

Validation gate — scripts/validate_corpus.py

2 · Per-track evidence

Track 1A — Rich answers (multimodal)

Two question sources, both with guaranteed-correct pixels. Fact plates are rendered programmatically (matplotlib), so numbers are exact — never trusted to a diffusion model. Visual attributes are concrete details forced into image prompts, then confirmed by the vision model (gpt-5.6-sol) before a question may exist; 6 of 9 verified in the pilot, and unverified images simply stay decorative.

“According to the figure plate depicting Ironfell Citadel’s military muster, how many troops are recorded in its garrison?” → 1096
The value 1096 exists only in plate_04.png, embedded in the Gazetteer codex. Gate check A1 confirms it appears in none of the 75 text documents.
“What is the central emblem on the banner of The Silent Choir?” → coiled serpent
Injected into the gpt-image-2 prompt, vision-verified present, and confirmed absent from all text (check A3). Visually inspected: the serpent is unmistakable.

Track 1B — Multi-hop across documents

The fact-placement planner assigns each hop of a protected chain to disjoint document sets — the property that makes a multi-hop question honest. Sample placements from the pilot answer key:

Checks B1/B2 verify this against the final text for all 8 pilot chains: no document contains both hops, and both hops are genuinely expressed. This closes the classic failure where the bridge entity’s own wiki page answers the “multi-hop” question in one retrieval.

Track 1C — Agentic, conflicting sources

Every disputed fact has an authority hierarchy enforced by placement: the true value only in the tier-1 codex, confident false claims only in tier-3 ephemera, and the wiki flags the dispute without resolving it. A naive single-document lookup plausibly lands on the false value; a corroborating search finds and weighs the canon source.

4 · Engineering evidence

  • 13/13 invariant tests pass (tests/test_competition_pipeline.py): unique names, temporal sanity (nobody fights before birth, artifacts wielded after forging), chain splitting, visual-only exclusion, dispute tiers, full fact coverage, renderer pagination, attribute well-formedness.
  • Deterministic and resumable: seeded generation; every stage caches to disk; interrupted runs continue with --run_dir. Credential preflight aborts a misconfigured run in ~2 seconds.
  • Leak-proof packaging: public/ (documents, images, answer-free sample_questions.json) is strictly separated from answer_key/ (world graph, placement matrix, dev/eval benchmarks with answers, verification reports). Gate check E1 confirms every evidence path resolves inside public/ alone.
  • Dev/eval split is stratified per track (30% dev by default); releasing answers later requires no rework, since answers live in a separate file.
  • Question answers are composed from ground truth, not by an LLM — the reasoning model only phrases the question; the graph supplies the answer and the placement matrix supplies provenance.

6 · Remaining gaps

None of these block generating the full corpus. Gaps 1–2 should be closed before the competition launches; the rest are judgment calls.

  • G1No difficulty calibration yet. The strongest missing evidence: a baseline RAG system (naive embed-and-retrieve, models already configured in .env) should be run against the corpus. If naive top-k answers most 1B/1C questions, chains and disputes need hardening; if nothing can answer them, they’re unfair. Recommended before launch.
  • G2No scoring harness for submissions. The benchmark provides questions, answers, aliases, and provenance — but the judging protocol (exact match vs. LLM-judged, partial credit for evidence citation) is not built. Decide and script it before evaluation week.
  • G3Full-scale run not yet validated. All evidence above is pilot-scale. The gate and tests run identically at full scale, but rate-limit behavior and the fact-miss rate at ~410 documents are unverified until the run happens. The gate is the backstop.
  • G4Page count vs. challenge wording. The challenge document says “thousands of pages”; defaults produce ~1,100. Scaling knobs exist (--volumes, --chapters, --ephemera, entity counts) if ~2,000+ pages is wanted; cost scales linearly.
  • G5Question volume. ~55–65 verified questions at full scale. Sufficient for judging; raise protected_chains, visual_only_facts, and disputes in the planner scale if a larger held-out set is preferred.
  • G6Human read-through. Prose spot checks were strong (atmospheric, in-world, consistent), but a full-corpus skim of 2–3 chapters, wiki pages, and one codex per book is a pre-release step no automation replaces.

7 · Launch checklist

  • Run python scripts/generate_competition_corpus.py --stages all (own terminal; resumable).
  • Run python scripts/validate_corpus.py --run_dir output/competition_<ts> — require GO.
  • Close G1: baseline RAG calibration run; adjust and regenerate if needed.
  • Close G2: decide grading protocol; script the scoring harness against answer_key/benchmark_eval.json.
  • Human skim (G6). Then distribute public/ only.
